# 신호·방향지시등·정지선 최종 융합 제어

`final_ws_bringup.launch`의 기본 제어 경로:

```text
GPS + IMU -> EKF -> 경로 Pure Pursuit -> 차선 fallback
                                          |
카메라 방향별 신호 + 정지선 + 경로 --------> maneuver_fusion -> control_mux -> CtrlCmd UDP
LiDAR 장애물/합류 공간 + 보행자 정지 ------->      |              ^
                                                +-> LampControl UDP
```

`maneuver_fusion_node.py`가 정지선 제어를 담당하므로 기존 stopline wrapper는
이 모드에서 pass-through다. Fallback 뒤에서 브레이크 제한을 적용하고, 마지막
`control_mux`도 안전 정지와 명령 timeout을 검사한다. 신호가 허용돼도 장애물이나
보행자 정지를 해제하지 않는다. 종방향 명령은 모두 `longlCmdType=1`이다.

## 방향 판단과 점등

신호등의 화살표는 해당 방향의 **통행 허가**이고 목적 경로를 바꾸는 명령이 아니다.
최종 기본 모드는 `require_route_signal_context: true`다. 정적 MGeo의 신호등
`link_id_list`와 경로 전체 링크의 위치·진행 방향을 대조하고, `related_signal`의
직진/좌회전/우회전 의미를 사용한다. 도로 곡률만으로 교차로 회전을 결정하지 않는다.
평행 차로·반대 방향·겹치는 경로 등 모호한 연결은 UNKNOWN으로 정지한다.
경로의 해당 링크가 전부 포함되지 않으면 연결하지 않는다. 비보호 좌회전·유턴은
별도 정책이 없어 UNKNOWN이다. 기본 30m/25도 추정은 레거시 시험 모드에서만 사용한다.

조향 노드가 발행한 `/experimental/curvature_reference_path`와 신호 판단에 사용한
대회 경로의 전체 점 개수·순서·XYZ 좌표·map 좌표계를 비교한다.
`require_reference_path_match: true`가 기본이며, 경로 미수신/불일치이면 정지하고
GPS 음영 차선 유지 예외도 차단한다. 정적 latched 경로이므로 발행 시각이 오래됐다는
이유만으로 무효화하지 않는다. 경로가 다시 일치해도 신호 확인과 방향지시등 선행 시간을
새로 확보해야 한다. 경로 파일을 바꿀 때는 두 노드를 같은 파일로 다시 실행한다.

| 대회 경로의 방향 | 확인된 신호 | 동작 |
|---|---|---|
| 직진 | 좌회전 전용 `LEFT`/`RED_LEFT` | 정지선 대기, 방향지시등 OFF, 직진 경로 유지 |
| 직진 | 직진+좌회전 `GREEN_LEFT` | 다른 진입 조건 충족 시 직진 |
| 좌회전 | 일반 녹색 `GREEN` 또는 우회전 전용 | 정지선 대기, 좌회전 경로 유지 |
| 우회전 | 좌회전 전용 | 정지선 대기, 우회전 경로 유지 |
| 경로 연결 불명확 | 어떤 허가 신호라도 | 방향을 추측하지 않고 정지 |

`maneuvers`의 수동 `turn`은 유일하게 연결된 MGeo 경로 조작과 방향이 같아야 한다.
충돌하거나 연결이 없으면 설정 오류로 시작을 거부한다. 일치하는 수동 항목은
지도 이벤트의 확인용이며, 별도 중복 이벤트를 만들거나 지도 경로를 바꾸지 않는다.
신호 확인 이력과 진입 허가는 이벤트 ID 외에도 방향·지도 링크·정지 위치·출구·
신호등 ID에 연결한다. 같은 ID라도 진행 의도가 달라지면 이전 허가를 재사용하지 않는다.
카메라가 정지선 접근 거리를 보정하는 것만으로 진행 의도가 바뀌지는 않는다.

`/control/maneuver_status`의 `route_direction`은 대회 경로의 방향,
`signal_allowed_directions`는 현재 확인된 대상 신호의 허용 방향,
`route_signal_compatible`은 두 방향의 일치 여부다. 실제 진입은 `permission`으로 확인한다.
`reference_path_match`와 `reference_path_reason`으로 조향 경로 일치 여부도 확인한다.
허가 후 교차로에 진입한 차량은 같은 대회 경로로 교차로를 빠져나온다. 그 뒤 보이는
다른 방향 화살표가 새 회전 명령이 되지 않으며, 장애물·위치 이상 정지는 계속 적용한다.

지도는 **신호등의 위치와 연결 관계만** 제공한다. 현재 색은 시나리오 JSON이나
MGeo의 `value`를 읽지 않고 `/detection/traffic_light`의 실제 카메라 검출에서 얻는다.
영상 시각과 50ms 이내의 EKF 자세로 대상 신호등을 영상에 투영한다. 검출 bbox와
유일하게 대응해야 하며, 다른 신호등도 대응 가능하면 UNKNOWN이다. 화면 중앙이나
최대 신뢰도만으로 신호등을 고르지 않는다. 좁거나 낮게 보이는 신호등을 배제하던
기존 가로세로 비율/높이 필터는 제거했다.

동일 신호등·동일 허가 상태를 서로 다른 영상 3개 이상, 0.3초 이상 확인한다.
동일 영상의 재처리는 횟수에 포함하지 않고, 적색/황색/모호한 관측은 허가를 즉시
취소한다. 카메라 timeout, 경로 변경, 위치 품질 저하도 확인 이력을 초기화한다.
`/control/maneuver_status`의 `selected_signal_id`, `selected_signal_state`,
`signal_selection_reason`, `route_context_count`로 판단 근거를 확인한다.

실제 YOLO용 Cam4/1131 카메라 보정이 저장소에 없어 `signal_camera.calibrated=false`가
기본이다. 원본 해상도·수평 FOV·장착 위치/방향·지도 위치/높이 정렬을 검증하기 전에는
교차로 통행을 허가하지 않는다. 차선 카메라 설정을 복사해서 우회하면 안 된다.
투영은 왜곡 없는 핀홀, 중앙 주점, 정사각 픽셀, 카메라 roll=0을 가정한다.
이 조건을 만족하지 않는 카메라는 먼저 보정 모델을 확장해야 한다.

`/perception/traffic_light/directional_state`는 전체 검출의 진단용 방향 정보다.
엄격 모드의 통과 허가는 이 집계가 아니라 위의 경로 연결·영상 확인 결과로 결정한다.
`GREEN`은 직진과 우회전, `LEFT`/`RED_LEFT`는 좌회전, `RIGHT`/`RED_RIGHT`는
우회전만 허용한다. `GREEN_LEFT`/`GREEN_RIGHT`는 직진과 해당 방향을 함께 허용한다.
이 의미는 기존 YOLO 클래스의 점등 조합 계약이며, 사용 모델의 실제 라벨과 맞춰야 한다.
서로 다른 신호등의 상충 결과를 합쳐 허가하지 않는다. 일반 `Arrow`, 낮은 신뢰도,
오래된 결과는 UNKNOWN이다. 황색과 적색은 정지한다. 적색 우회전은 구현하지 않았다.
`right_on_green: false`를 설정하면 우회전 화살표가 있어야 허용한다.

### GPS 음영구간의 제한된 차선 유지

최종 런치에서 `enable_lane_fallback=true`이면 통합 제어도 최신
`/stability/camera_fallback_status`를 확인한다. 이전처럼 GPS_BLACKOUT이라는
이유만으로 모든 차선 유지 명령을 폐기하지는 않지만, **교차로 진입 허가와 분리**한다.
정상 GPS·경로 위치와 정상 fallback 상태를 먼저 확인한 이력이 있어야 하며,
활성 조작이 없고, 알려진 다음 교차로/차선 변경의 접근 범위 밖이며,
현재 영상에 정지선·신호등이 없는 경우에만 저속 차선 유지가 가능하다.
접근 범위는 최소 40m이며 속도에 따라 늘어난다. 미확인/오래된 영상은 빈 영상으로
취급하지 않는다. 지도 연결이 없거나 카메라 상태·IMU·속도·장애물 안전 입력이
불량하면 정지하며, 음영구간의 새로운 좌/우회전이나 차선 변경은 허가하지 않는다.

기본 예산은 최근 정상 위치 이후 15초 또는 이동 30m다. 하나라도 초과하거나
제어 시간이 끊기면 예외를 중지한다. 이동량은 속도 적분과 경로상 위치 변화로 제한하며
GPS 복구 후 차선 제어의 실제 안정화·조향 전환이 끝나기 전에는 기준점을 갱신하지 않는다.
`blackout_lane_corridor=true`는 이 제한된 차선 유지 예외이며 `permission=true`라는
교차로 진입 허가가 아니다. `blackout_corridor_reason`에 허용/거부 이유를 표시한다.
상세 조건과 검증 한계는 [차선 fallback 설명서](CAMERA_LOCALIZATION_FALLBACK.md)를 참고한다.

좌·우회전 의도가 확정되면 해당 방향지시등을 켜고, 최소 5초 연속 UDP 송신 후
신호 허가를 확인해 출발한다. 시뮬레이션 시간과 실제 경과시간 모두 5초를 요구한다.
송신 실패·입력 끊김·방향 변경은 점등 시간을 초기화한다. UDP 성공은 송신 성공이며
시뮬레이터의 램프 점등 ACK는 아니다. 실제 점등은 MORAI에서 확인해야 한다.

정지 목표는 앞범퍼 기준이지만, **신호 진입 판정은 앞바퀴 축 기준**이다.
`turn_entry_front_axle_offset_m=3.0`은 뒤차축 기준 원점에서 앞차축까지의 거리다.
앞범퍼 오프셋 3.845m와 혼용하지 않는다. 지도 정지선이 검증돼 있으면 카메라 오차로
정지 목표를 앞당겨도 신호 진입선까지 앞당기지 않는다. 이 판정은 경로 진행거리와
축거를 이용한 근사이며, 실제 앞바퀴 접촉 위치·횡방향 오차는 MORAI에서 검증해야 한다.

진입선 앞에서 발급한 최신 허가(기본 최대 0.5초)와 **진입하는 현재 주기의 신호·
방향지시등·센서·안전 조건**을 모두 확인한 경우에만 진입 완료로 전환한다.
진입 순간 적색/미확인 신호, 송신 실패, 장애물 정지, 제어 공백이 발생하면 이전 허가를
재사용하지 않는다. 확인 없이 진입선을 넘거나 교차로 안에서 노드를 시작한 경우
`entry_fault=true`, `entry_without_current_permission`으로 정지를 유지한다.
뒤늦은 초록불이나 링크 끝 도달로 이 오류를 자동 해제하지 않는다. 정지 상태에서
원인과 위치를 확인하고, 시뮬레이터를 진입선 이전의 안전한 시작 위치로 복구한 뒤
주행 상태를 재초기화해야 한다. 교차로 내부에서 노드만 재시작해도 허가는 생기지 않는다.

허가를 확인하고 앞차축이 정지선을 통과한 조작은 경로 끝까지 유지한다. 회전 도중
신호등이 시야 밖으로 사라져도 같은 조작을 이어가되 장애물 정지는 계속 적용한다.
좌·우회전 종료는 해당 MGeo 링크의 실제 경로상 끝에 도달하고, 현재 차량의 출구
방향 오차가 15도 이하이며 경로 이탈이 0.75m 이하일 때 확인한다(초기 기본값).
종료한 tick 안에 다음 교차로를
다시 검색하고 신호 확인 이력을 초기화하여 이전 녹색 허가를 넘기지 않는다.
연속 교차로가 같은 방향이어도 새 조작의 5초 점등 조건을 다시 확인한다.
이미 진입한 회전 중 위치 품질이 나빠지면 제동하되 해당 방향지시등 송신은 유지한다.
정상 위치 정보로 종료 지점을 확인한 뒤 끄거나 다음 조작 방향으로 전환한다.
방향지시등 선행 시간은 두 시계 모두 연속성을 검사하며, 시간 점프·NaN·불완전 송신은
점등 시간으로 누적하지 않는다. 이미 진입한 뒤의 UDP 송신 실패는 점등 ACK가 없으므로
실제 램프 상태를 알 수 없으며, 송신을 재시도한다. 램프 고장만으로 새 회피 경로를 만들지는 않는다.
현재 교차로 안에서도 다음 정지선에 대한 독립 제동 제한을 적용한다. 차량 길이보다
교차로 사이가 짧으면 뒷차축이 이전 링크 끝에 닿기 전 정지할 수 있으며,
`next_junction_guard`가 유지되면 지도상의 종료 경계를 현장에서 재검증해야 한다.
현재 대회 경로의 6개 연결 구간은 이처럼 겹치지 않는다. 임의로 가속해 해제하지 않는다.

차선 변경은 기존 경로에 변경 구간이 포함돼 있어야 하며 `maneuvers`에
`kind: lane_change`, `start_s_m`, `end_s_m`, `direction`을 등록한다. 5초 점등과
해당 방향의 최신 LiDAR `confirmed_available`을 모두 요구한다. 비어 있는 목록에서도
MGeo 기반 교차로 판단은 동작한다. 수동 조작과 지도 교차로는 시작거리 순으로 처리하고,
같은 시작점에서는 지도 연결을 우선한다. 신호 제어 구간과 겹치는 차선 변경은 거부한다. 지도와
연결되지 않은 수동 회전은 엄격 모드에서 통행을 허가하지 않는다.
이 코드는 새로운 차선 변경 궤적을 생성하지 않는다.

### 공통 곡률 속도와 회전 자세 검사 (2026-09-09)

`src/turn_signal_controller/turn_motion.py`의 `TurnMotionPlanner`를 최종
`maneuver_fusion_node.py`에 연결했다. 방향별 신호 허가, 선행 점등, 정지선 제어를
유지하면서 회전 진입 전부터 속도를 제한한다. Pure Pursuit가 보낸 조향값은 유지한다.
따라서 좌회전 신호가 직진 경로를 자동으로 좌회전 경로로 바꾸지는 않는다.

| 설정 | 초기 기본값 | 용도 |
|---|---:|---|
| launch `max_speed_kph` | 7.2km/h | 직진·좌회전·우회전에 공통으로 적용하는 전체 최고속도 |
| launch `lateral_accel_limit_mps2` | 1.0m/s² | 모든 방향의 곡률 속도 계산에 공통으로 쓰는 계획 횡가속도 한계 |
| `turn_max_heading_error_deg` | 60도 | 경로 방향 대비 큰 자세 오차 시 정지 |
| `turn_max_lateral_error_m` | 1.5m | 경로에서 크게 벗어난 경우 정지 |
| `turn_exit_heading_error_deg` | 15도 | 회전 완료에 필요한 출구 방향 정렬 |
| `turn_exit_lateral_error_m` | 0.75m | 회전 완료에 필요한 경로 정렬 |
| `turn_exit_overrun_m` | 3m | 종료점 이후 정렬 확인을 기다리는 최대 거리 |

기존의 `turn_left_speed_kph: 15`, `turn_right_speed_kph: 10` 방향별 상한을 제거했다.
별도 `turn_lateral_accel_mps2: 1.2`도 제거했으며, 이전 YAML에 남아 있으면 무시하고
경고한다. 이 세 항목은 삭제하고 위의 두 launch 인자를 사용한다. 공통 속도 인자는
nominal 곡률 계획과 fusion에 함께 전달되며, 자세 관련 항목은 기존 YAML에 둔다.

두 제어기는 `curvature_speed_mps()`를 공유해
`v_curve[km/h] = 3.6 * sqrt(lateral_accel_limit_mps2 / abs(곡률[1/m]))`로 계산한다.
같은 곡률과 횡가속도 한계이면 좌·우회전 속도는 같고, 곡률이 커지면 속도는 작아진다.
직선처럼 곡률이 0에 가까우면 곡률 제한 없이 전체 최고속도와 가감속·종점 정지 제한을
적용한다. 초기 횡가속도 1.0m/s²에서 이상적인 반경 5/15/40m의 곡률 속도는 각각
약 8.0/13.9/22.8km/h다. 이는 전체 최고속도와 다른 감속 조건을 적용하기 전의 값이다.

nominal 노드는 경로 전체에 곡률과 가감속 한계를 적용한 속도 프로파일을 만든다.
fusion은 정적 경로를 1m 간격으로 다시 샘플링하고, 남은 회전 구간에서 가장 큰 곡률로
추가 접근 제한을 계산한다. 따라서 두 곡률 추정의 샘플링·확인 구간은 다르지만
계산식과 물리 파라미터는 같다. 방향별 고정 상한은 없다.
회전 전에는 앞차축 진입 경계까지의 남은 거리,
계획 감속도와 반응시간을 반영해 접근 속도 상한을 만든다. 초록불이어도 현재 속도가
이 상한보다 높으면 감속하며, 기존 정지선·보행자·장애물 제동보다 약하게 만들지 않는다.
접근 속도도 공통 `max_speed_kph`를 초과하지 않는다.
기존 `NOMINAL`/정지 상태를 보존하므로 속도 제한 자체가 신호 진입 허가를 없애지는 않는다.

차량 quaternion이 없거나 유효하지 않으면 회전을 허가하지 않는다. 현재 경로 접선과
차량 방향의 차이 또는 횡방향 오차가 기준을 넘으면 제동한다. 진입 전 자세 이상은
누적 신호 허가도 취소하며, 복구 후 새 신호 관측을 다시 확인한다. 이미 진입한 회전은
안전 정지를 적용하되 방향지시등을 유지한다.

경로상 종료 위치만 지났다고 회전을 완료하지 않는다. 출구 방향과 경로 위치가 함께
맞아야 완료하며, 정렬 대기 중에는 곡률·전체 최고속도 제한과 방향지시등을 유지한다. 종료점보다
3m 이상 진행해도 정렬되지 않으면 `turn_exit_alignment_unconfirmed`로 정지한다.
별도의 회복 궤적을 생성하거나 핸들을 고정 각도로 꺾는 기능은 아니다.

현재 저장소의 대회 경로를 읽어 계산한 회전 구간은 다음과 같다. 아래 속도는 계획
상한이며 실제 주행 성능을 측정한 값은 아니다.

| 방향 | 경로 누적거리 구간 | 최대 남은 곡률 | 곡률만의 속도 상한 (횡가속도 1.0) | 전체 최고속도 기본값 적용 후 |
|---|---|---:|---:|---:|
| 우회전 | 약 550.62~580.87m | 약 0.114498/m | 약 10.64km/h | 7.2km/h 이하 |
| 좌회전 | 약 609.88~635.11m | 약 0.094711/m | 약 11.70km/h | 7.2km/h 이하 |

`/control/maneuver_status`에 `turn_phase`, `turn_speed_limit_kph`,
`turn_curve_speed_kph`, `turn_heading_error_deg`, `turn_lateral_error_m`,
`turn_exit_heading_error_deg`, `completed_event_id`를 추가했다.
`turn_speed_limit_kph`는 전체 최고속도를 반영한 현재 위치의 접근 상한,
`turn_curve_speed_kph`는 전체 최고속도를 적용하기 전 곡률만의 상한이다.
곡률 제한이 없는 직선은 후자가 null이다. `turn_curvature_abs_m_inv`,
`lateral_accel_limit_mps2`, `max_speed_kph`로 어떤 계산값·공통 상한이 적용됐는지 확인한다.
`turn_phase`는 `APPROACH`, `TURNING`, `EXIT_ALIGNMENT`, `NONE`이다.
완료한 주기에는 `completed_event_id`를 발행하며 다음 이벤트에는 이전 허가를 넘기지 않는다.

`test_turn_motion.py`는 실제 Pure Pursuit 조향 함수와 실제 fusion callback을
반지름 15m의 좌·우 90도 경로 및 단순 bicycle 차량 모델에 연결한다. 정지선 대기,
5초 점등, 대응 화살표 확인, 진입 후 신호 미검출, 출구 정렬·소등을 검사한다.
방향별 고정 속도 대신 같은 반경의 좌·우회전 속도와 제동이 같음을 검사하고,
반경에 따른 속도 변화, 전체 최고속도, 작은 횡가속도 한계의 감속 효과도 검사한다.
이 시험은 합성 경로와 이상적인 제동·조향 모델의 결과이며 실제 MORAI 검증을 대신하지 않는다.

관련 회귀 테스트는 신호·회전 190개, 정지선 54개, 카메라 67개, 음영/센서 41개,
곡률 계획 7개로 총 359개 통과했다. 실제 Cam4 보정값은 여전히 미설정(`calibrated: false`)이므로
실제 교차로 통과를 허가하기 전에 카메라 투영과 차량 기준점을 확인해야 한다.
일반 녹색 우회전은 기존 `right_on_green: true` 정책을 유지하며, false이면
`RIGHT`/`RED_RIGHT`/`GREEN_RIGHT`와 같은 우회전 화살표가 필요하다.

## 앞범퍼 0.5m 정지 목표

```text
앞범퍼~정지선 거리 = BEV ego~정지선 거리 - 앞범퍼 오프셋 - 영상 지연 중 이동거리
남은 제동거리      = 앞범퍼~정지선 거리 - 0.5m
```

기본 앞범퍼 오프셋 `3.845m`는 저장소의 뒤차축 base_link 가정과
`vehicle_model.yaml`의 휠베이스 `3.000m` + 앞 오버행 `0.845m`를 사용한다.
MORAI 차량 원점이나 BEV 좌표 원점이 다르면 `stopline_front_reference_offset_m`을
실측해 바꿔야 한다. 차체 중심을 원점으로 쓰는 경우 3.845m를 그대로 쓰면 안 된다.

속도에 따른 제동거리와 반응 지연을 반영해 감속하고, 목표 근처에서는 제동을 유지한다.
영상 거리에는 수신 이후 지연을 보정한다. 별도 미측정 센서 내부 지연은 포함되지 않는다.
정적 지도에서 `on_stop_line` 노드까지 경로 연결이 검증된 경우, 카메라 미검출에도
그 지도 목표를 EKF 진행거리와 결합한다. 정지선이 확인되지 않은 링크 진입점은
보수적 정지용으로만 사용하며, 녹색이어도 카메라의 일치 관측 전에는 통과하지 않는다.
지도 연결이 없는 곳에서 신호등/정지선을 보면 UNKNOWN 정지를 유지한다.
레거시 모드의 카메라 정지선 소실은 최대 8초/12m 속도 추정으로만 보완한다.
오도메트리 끊김·시간 역행·예측 유효 범위 초과는 정지 처리한다.
0.5m는 제어 목표이며 실제 오차는 카메라 보정과 MORAI 제동 응답에 달려 있다.

## 실행과 확인

### 신호 관측 순서와 지연 보호 (2026-09-09)

- 통합 노드는 callback에서 수신한 신호 영상들을 최대 32개 대기열에 보관해 원본
  시각의 순서로 처리한다. 제어 주기 사이 RED→LEFT가 연속 수신되어도 이전 통과
  허가와 진입 ticket을 취소하고 허용 신호를 다시 확인한다. 이미 유효하게 진입한
  교차로 내부의 통과 정책과 긴급정지 보호는 그대로 유지한다.
- 영상과 50ms 이내의 지도 좌표 pose가 아직 없으면 해당 영상을 보류한다. pose가
  뒤늦게 도착하면 같은 영상을 재평가하되, 원본 stamp와 최초 수신 시각을 유지한다.
  보류 중에는 통과를 허가하지 않으며 새 영상이 미처리 과거 영상을 건너뛰지 않는다.
  만료된 영상은 폐기하며 같은 프레임의 반복 timer 처리는 확인 횟수를 늘리지 않는다.
- 대기열 초과나 동일 시각의 서로 모순되는 신호 관측은 기존 허가를 무효화한다.
  이후 새 시각의 유효 관측으로 재확인해야 한다. ROS 신호/객체 구독 대기열도 32로
  맞췄지만, callback 도착 전 네트워크·상위 노드에서 유실된 관측까지 보장하지 않는다.
- 속도 정보 소실, 0.5초 초과 제어 공백(기본값), 유효하지 않은 제어 시각 이후에는
  이전 GREEN 확인 이력을 재사용하지 않는다. 정상 데이터 복구와 새로운 허용 신호
  확인이 필요하다. 같은 ID의 지도 정지 목표 재확인에 의한 보수적 접근은 유지한다.

`/control/maneuver_status`에서 `signal_pending_frames`, `signal_queue_overflows`,
`signal_processed_stamp`, `signal_selection_reason`, `permission`, `entry_fault`를
함께 본다. `signal_pose_unsynchronized`는 pose 대기, `signal_queue_overflow`는
대기열 초과, `signal_duplicate_conflict`는 동일 시각 충돌이다. 회귀시험은
`test_signal_temporal_safety.py`에 있으며 실제 센서 지연·MORAI 제동 검증을 대체하지 않는다.

### 실행 절차

시나리오 로드, 네트워크, Cam4 보정, 저속 단계별 시험은
[시나리오 주행 시험 가이드](SCENARIO_DRIVING_TEST_KO.md)를 먼저 따른다.

Ubuntu ROS Noetic에서 새 패키지를 빌드한다.

```bash
cd ~/morai_ws
catkin_make
source devel/setup.bash
roslaunch morai_bringup final_ws_bringup.launch enable_control:=false
```

기본 미리보기에서는 차량 제어 UDP와 LampControl을 모두 송신하지 않는다.
Ego 상태 수신과 ROS 내부 판단은 유지된다. 실제 제어 실행:

```bash
roslaunch morai_bringup final_ws_bringup.launch \
  enable_control:=true morai_host_ip:=192.168.0.151 \
  turn_signal_remote_port:=9097 \
  turn_entry_front_axle_offset_m:=3.0 \
  stopline_front_reference_offset_m:=3.845 stopline_hold_distance_m:=0.5
rostopic echo /control/maneuver_status
rostopic echo /control/turn_signal_state
```

MORAI Network Settings에 **TurnSignalLampControl 수신 UDP**의 IP/포트를 맞춘다.
패킷은 저장소의 `TurnSignalLampControl.py` 정의와 동일한 33바이트다.
네트워크 설정 위치는 [MORAI 공식 UDP 설정](https://help-morai-sim.scrollhelp.site/ko/morai-sim-drive/24.R2/udp)을 참고한다.
기존 lamp-only `turn_signal_controller.launch`는 독립 송신 실험용으로,
최종 통합 런치와 동시에 실행하면 안 된다. 그것만으로 조작 지연을 제어하지는 않는다.
독립 lamp-only 모드에서 `end_s_m` 없이 `duration_sec`을 사용할 때는 선행 점등 시점이
아니라 `start_s_m` 도달 시점부터 유지 시간을 센다. 신호 대기 중 먼저 꺼지지 않는다.

상태 확인 항목:

- `lamp_requested`: 요청한 OFF/LEFT/RIGHT, `lamp_transmit_ok`: 이번 UDP 전체 송신 성공.
  둘 다 실제 MORAI 점등 ACK가 아니다.
- `indicator_ready`: 연속 선행 점등 조건, `permission`: 이번 제어 주기의 통행 허가.
- `entry_reference_offset_m`, `entry_crossing_s_m`: 앞차축 보정값과 경로상 진입 경계.
- `event.committed`: 유효 허가로 진입했는지, `entry_fault`: 무허가/미확인 진입 오류.

추가 회귀시험은 앞범퍼/앞차축 구분, 진입 순간 신호 변경·송신 실패·장애물, 제어 공백,
교차로 내부 재시작, 우회전 정책 전환, 회전 종료 소등, 연속 회전 점등 재확인을 포함한다.

검증은 ROS 대역/UDP 송신 mock, 단순 종방향 차량 모델과 실제 Pure Pursuit 함수를
연결한 bicycle 모의 주행으로 수행했다.
실제 ROS 빌드, MORAI 점등, 실차량 정지 오차와 경로 방향 판정은 이 Windows 환경에서
실행하지 않았다. 다른 모델/맵/차량 원점에 대한 자동 보정 기능은 없다.
